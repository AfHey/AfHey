# Cross-Review of Pre-Phase-1 Documents (Claude, 2026-08-30)

Adversarial second review, run after the 60-item external review was applied. Scope: `CLAUDE.md`, `product-spec.md`, `architecture.md`, `decisions.md`. Goal: contradictions, undefined terms, phaseless requirements, decisions missing from the log, and anything leaving the Phase 1 Prisma schema or Proposal model ambiguous. All findings below are fixed in the same commit unless listed under "Left unresolved."

## Findings fixed

1. **`find_free_time` contradiction.** §7.1.5 listed it as a composed operation, and §7.1.4 requires composed operations to return Proposals; §12.3 models the same capability as the read-only primitive `get_free_time`, which returns data. Removed from the composed list with a supersession marker.
2. **Event `kind = deadline` undefined.** It appeared only inside the §9.2 enum, with no semantics anywhere, inviting duplication of Task deadlines as stored Events. Removed from the enum; externally imposed dates are Task `deadline_*`, calendar deadline display is derived at render time.
3. **Undo-of-create deadlock.** "Hard deletion is rejected while any dependent or audit reference exists" made batch undo impossible: every Proposal-created entity has an ActionLog reference from birth. Clarified: dependents block undo deletion; ActionLog snapshots reference UUID values without foreign keys and never block it. Hard delete exists only as undo-of-create.
4. **`applying` status had no semantics.** Defined as the approval-to-commit window only, with crash recovery resolved via the idempotency key (ActionLog present → `applied`, absent → `failed`, re-approvable).
5. **`origin = user` undefined.** The §11 origin table had no `user` row, and it was unclear whether manual edits go through Proposals. New Rule 13: user origin covers undo and future user batch flows; ordinary manual single-entity edits are direct transactional mutations (revision bump, no Proposal/ActionLog); Quick Add stays `origin = inbox`.
6. **Phase 1 approval policy covered only Inbox Proposals.** Phase 1 also produces batch-undo Proposals. Rule 7 now states every Phase 1 Proposal uses `approval_policy = explicit`.
7. **Evidence and retention inconsistency.** FieldEvidence offsets had no defined basis text; raw text expired at 30 days while redacted text and evidence literals apparently persisted forever, undermining retention (the guard is last-resort, so redacted text can still hold sensitive content). Pinned: `redacted_text` is the exact transmitted guarded payload; offsets index into it; the expiry job nulls raw text, redacted text, and evidence literals together.
8. **Phase 1 table set was ambiguous.** `Proposal.conversation_id` referenced a Conversation table that is Phase 3b; UserSettings constraint children had no phase; auth needed tables ("password or passkey", "session rotation and revocation") that did not exist in the data model. Added the "Phase 1 migration boundary" paragraph to §9 (exact Phase 1 table list, constraint children in Phase 2, Conversation/Message/TurnReferenceSet and `conversation_id` in Phase 3b) and defined `Credential` and database-backed `Session`.
9. **Notes missing from Phase 1 scope lists.** Extraction and no-AI mode create Notes, but §15 Phase 1 and CLAUDE.md omitted them. Added, along with WorkSession, GlossaryEntry, duplicate warning, entity resolution, and minimal settings (timezone + glossary CRUD) — settings management previously had no owning phase at all.
10. **§5 cited a decision the log never recorded.** The week/month-view deferral marker pointed at "Release boundaries and phase ownership," which said nothing about calendar views. Amended that entry (marked as a same-day cross-review amendment).
11. **Overlap validation over-rejected.** "Fixed-event overlaps" as a universal validation failure would block legitimate double-booking of real commitments. Split: scheduler-placed blocks may not overlap fixed Events or other blocks; user-approved fixed-with-fixed overlap warns.
12. **Smaller fixes.** §9 preamble now covers PersonAlias/GlossaryEntry (common mutable), FieldEvidence/TurnReferenceSet (immutable), and join rows; §3.1.5 no longer implies the Capture record is created at confirmation; §10.5 defines what completing a task does to its blocks and that task "delete" is archive; `block_state = in_progress` has a trigger (active WorkSession); deterministic priority-score recomputation is assigned to Phase 2; extraction may not propose `kind = block` Events (no blocks exist before Phase 2); operation `entity_type` Phase 1 values enumerated; architecture.md gains `core/auth/` and `jobs/` boundaries, auth-endpoint rate limiting (spec had it, architecture dropped it), and the retention wording matching the spec.

Three new decision-log entries record the substantive choices; the spec header is bumped to Version 1.1.

## Left unresolved for the product owner

1. **One or two Phase 3b reasoning models.** §12.1 says complex requests "may be routed to a stronger reasoning model," while the pending decision pins "the exact Phase 3b text-reasoning model" (singular). When that decision is made, state whether it pins one model or a primary + escalation pair. Gated by the existing pending item; nothing changed now.
2. **Duplicate-detection thresholds.** §3.1.4 "title similarity plus same project or same due window" stays qualitative. Fine to pin during Phase 1 implementation via tests, but say so if you want exact thresholds in the spec instead.
3. **`Person.last_contact_at` has no V1 update source.** Until Phase 5 integrations it can only be edited manually. Harmless; flagging so it is not mistaken for an automated field.
4. **Capture rows for fully rejected Proposals.** There is no `rejected` processing status; such Captures sit in `proposed` until the 30-day cleanup discards them. Acceptable under the current retention rule; add a status only if you want them distinguishable before expiry.
